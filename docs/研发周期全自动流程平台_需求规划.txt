【已锁定决策 · 2026-09-25】
----------------------------------------------------------------
D1 部署网络：仅公司内网。服务端/客户端同内网，反向长连接即可，鉴权与传输加密可简化。
D2 coding agent 自主度：全自主无干预。但必须配套四道安全护栏（见第六节），
   即"分支隔离 + 自动测试门禁 + 仅 MR 不直推主干 + 失败自动回滚"。
D3 客户端技术栈：Go 单文件 daemon（跨平台、无运行时依赖、常驻研发电脑）。
D4 模型与 coding agent 后端：服务端 LLM QA（准入/分拣/QA 问答）走公网 API（千问/智普）；
   文档生成与代码执行统一由客户端 coding agent 完成，coding agent 支持多后端可配置
   （ClaudeCode / Cursor / Codex / CodeBuddy），其中 CodeBuddy 为内部私有化后端；
   代码相关（故障分析/编码/需读代码的文档）默认走私有化后端，敏感仓库由服务端按项目
   策略强制私有化，公网后端（Claude/Cursor/Codex）允许用户在本人客户端自选（合规自负）。
D5 配置归属：coding agent 的 prompt 模板、模型、限额等由服务端统一配置，并支持按
   客户端/责任人差异化覆盖；客户端拉取本人配置执行，回传渲染结果与状态，服务端聚合可见。


一、项目背景与目标
----------------------------------------------------------------
背景：
- 当前研发周期中，需求/缺陷从提出、准入、分发到执行，大量环节依赖人工传递与人工推动，
  责任人之间信息不同步，过程文档散落各处，管理层难以实时看到进度与产出物。
- 你希望把"issue 录入 → 准入判定 → 项目分拣 → 工作流执行 → 文档沉淀"整成一条
  服务端编排、客户端执行的自动化流水线，并用两类 AI（服务端大模型 QA + 客户端 coding agent）
  替代其中的分析与编码人力。

目标（建议表述，可改）：
- 系统 shall 提供统一的 issue 录入入口，覆盖需求与 bug 两类。
- 系统 shall 基于知识库自动完成 issue 准入判定与项目分拣，减少人工分派。
- 系统 shall 按预设工作流编排执行任务，并通过 CS 通道驱动责任人客户端落地。
- 系统 shall 把每个环节的过程文档（概要/设计/故障报告/修复方案等）回传服务端集中可见。
- 系统 shall 对录入、判定、查看、执行等能力做基于角色的权限控制。
- 系统 shall 保证所有 AI 调用（含变量替换后的最终 prompt 与调用日志）在服务端可观测。

三、整体架构（CS）
----------------------------------------------------------------
【关键】"服务端通过 gRPC 连接客户端电脑"在真实网络里是"反向长连接"模式：
- 客户端（研发电脑上的 Go daemon）主动向服务端建立持久 gRPC 流（stream）+ 心跳；
  服务端通过已建立的流把任务指令"推"下去（研发电脑在 NAT/防火墙后，服务端无法主动入站）。
- CI runner（GitLab Runner、GitHub Actions）、RMM 工具均为此模型。

组件：
- Server（服务端）：issue 录入/准入/分拣/工作流编排/权限/文档存储/AI 编排/可观测。
- Client（客户端 daemon，Go）：注册到服务端、收任务、调本地工具链（git/编译器/测试
  runner）与本地 coding agent（多后端可配）执行，产出文档与日志回传服务端。
- AI 网关（两类）：
  · 服务端 LLM QA（千问/智普，公网）：仅用于准入判定、项目分拣、通用 QA 问答（不涉及代码）。
  · 客户端 coding agent（多后端）：承担全部"需读代码"的工作——文档生成（概要/详设/
    故障报告/修复方案/评审辅助）+ 故障分析/编码/测试执行。
- 知识库（KB）：服务端侧，用于准入判定与项目分拣，支持向量检索（RAG）。

部署：服务端标准脚本部署（沿用你非 Docker 偏好）；客户端为单文件 daemon，一键安装。


四、核心流程
----------------------------------------------------------------
A. 录入（页面）
   必填：业务、诉求类型(需求|bug)、诉求描述、期望完成时间、责任人
   选填：优先级、关联需求/模块、附件

B. 准入判定（AI + 规则，服务端 LLM QA）
   基于 KB 判断该 issue 是否"可准入"（信息完整度、是否符合规范、是否重复、是否在范围内）。
   不合规则打回并给出原因。

C. 项目分拣（AI + 映射，服务端 LLM QA）
   依据 issue 内容（业务/描述）识别关联项目，解析出 Git 仓库地址。
   建议：业务→项目→Git 映射表（可配置）为主，AI 模糊匹配兜底。

D. 工作流编排与执行（服务端编排 + 客户端 coding agent 执行）
   需求流：拉取 Git → 需求分析(概要文档) → 详细设计(设计文档) → 设计评审(详设评审)
           → 编码 → 测试 → 验收
   Bug流： 拉取 Git → 问题分析(故障报告) → 方案设计(修复方案) → 设计评审(详设评审)
           → 编码 → 测试 → 验收

   每个节点：
   - 由服务端下发给责任人客户端（反向 gRPC 流）；
   - 文档类节点由客户端 coding agent 生成初稿（需读本地代码，故必须在客户端），
     回传服务端可见，责任人确认/修订；
   - 执行类节点（编码/测试）由客户端 coding agent 落地，结果回传；
   - 评审节点支持人工评审结论回写；
   - 每次 AI 调用的"变量替换后最终 prompt + 调用日志"回传服务端，issue/agent 视图可查。

六、AI 能力设计（职责边界 + 配置化 + 可观测）
----------------------------------------------------------------
两类 AI，职责按"是否需要读代码"切分：

1) 服务端 LLM QA（公网 API：千问/智普）
   - 用途（仅不涉及代码内容的场景）：issue 准入判定、项目分拣、通用 QA 问答。
   - 不负责文档生成（文档需读代码，统一交给客户端 coding agent）。
   - 接入：服务端统一网关，模型可切换、有额度控制；检索 KB 后拼入 prompt（RAG）。
   - Prompt：QA 相关 prompt 与模板落在服务端配置文件（F-21）。

2) 客户端 coding agent（多后端、可配置）—— 文档生成 + 执行
   - 文档类（需读本地代码，必须在客户端生成）：需求分析/概要文档、详细设计文档、
     故障报告、修复方案、评审辅助。基于本地仓库分析后产出，回传服务端可见。
   - 执行类：故障分析、编码、单测/集成测试执行。
   - 多后端可配置：同一台电脑可配置多个 coding agent 后端，至少支持
     ClaudeCode、Cursor、Codex、CodeBuddy（CodeBuddy = 内部私有化，用于敏感代码）。
   - 配置归属（D5）：由服务端统一配置 coding agent（prompt 模板、模型、限额等），
     并支持按客户端/责任人差异化覆盖；客户端拉取本人配置后执行，上报用量与状态，
     服务端聚合展示成本与配置状态。
   - 自主度：全自主无干预（D2），仍配套四道安全护栏：
       (a) 分支隔离：每次 issue 自动开独立 feature 分支，绝不直改主干；
       (b) 自动测试门禁：编码后自动跑单测/集成测试，不通过则禁止提 MR；
       (c) 仅 MR 不直推：agent 只提 Merge Request，合并留给责任人/评审人；
       (d) 失败自动回滚：测试失败或构建异常，agent 自动 revert 并上报服务端。
   - 合规：使用 Claude/Cursor/Codex 等公网后端做代码分析时，代码内容会发往对应厂商；
     敏感/内部仓库由服务端按项目策略强制走 CodeBuddy 私有化后端。

3) Prompt 与模板治理（强约束，F-21）
   - 所有 AI 相关 prompt 必须落在配置文件（服务端统管，D5），不得硬编码。
   - 需拼接的 prompt 以"模板 + 变量"形式放配置文件；变量由系统注入
     （issue 字段、仓库上下文、KB 检索结果、工作流节点等）。
   - 配置服务端统管并支持按客户端差异化；模板由服务端下发，客户端注入变量执行，
     回传渲染后的最终 prompt 与调用日志（F-20）。
   - 可观测性（F-20）：客户端每次 AI 调用必须把"变量替换后的最终 prompt"与
     "调用日志（模型、请求/响应摘要、token、耗时、费用）"回传服务端；
     服务端在 issue / agent 视图可查，用于调试 prompt、审计与成本管控。

4) 安全护栏（全自主四道，D2）
   见 2) 中 (a)~(d)。合并与最终验收保留人工闸门，属发布安全，不在 D2 让步范围。

知识库（KB）：
   - 用于"准入判定"与"项目分拣"的依据，也作为服务端 LLM QA 的 RAG 来源。
   - 内容建议：研发规范、历史 issue、项目地图、模块说明、评审 checklist。
   - 来源待确认：接入 Wind 内部 wiki / 平台内自建上传 / 二者结合。

八、关键风险与待确认（摘要）
----------------------------------------------------------------
R1 连通性：服务端无法主动连客户端 → 客户端反向长连接（已定 D1/D3）。
R2 coding agent 自主度：已定 D2（全自主无干预）+ 四道护栏；合并/验收留人工闸门。
R3 代码出网合规：已定 D4 —— 代码相关默认走 CodeBuddy 私有化；公网后端允许自选，
   敏感仓库由服务端策略强制私有化。
R4 文档可见性：客户端产出文档需回传服务端存储（对象存储/文件服务），需定存储方案。
R5 准入判定准确率：AI 判定需人审兜底，避免误杀/误放。
R6 Prompt/可观测治理：所有 prompt 配置化 + 渲染后 prompt 与调用日志回传，
   是调试与合规审计的硬要求，列为 P0（F-20/F-21）。
