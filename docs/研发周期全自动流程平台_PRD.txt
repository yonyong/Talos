研发周期全自动流程平台 — PRD（V0.1）
================================================================

文档信息
- 版本：V0.1（基于需求规划 V0.3 转化）
- 适用阶段：阶段二 PRD 撰写
- 需求描述遵循 EARS 原则：Ubiquitous(始终约束) / Event-driven(事件触发) /
  Unwanted(异常) / State-driven(状态) / Optional(可选)
- 已锁定决策：D1 内网部署 / D2 coding agent 全自主+四护栏 / D3 客户端 Go daemon /
  D4 服务端QA走公网·coding agent多后端·代码默认私有化 / D5 配置服务端统管且按客户端差异化

注：以下"系统"指本平台（服务端+客户端 daemon 整体）。


一、背景
----------------------------------------------------------------
当前研发周期中，需求/缺陷从提出、准入、分发到执行大量依赖人工传递与推动，责任人信息
不同步，过程文档散落，管理者难以实时看到进度与产出物。本平台将
"issue 录入 → 准入判定 → 项目分拣 → 工作流执行 → 文档沉淀"建成服务端编排、客户端
执行的自动化流水线，并以两类 AI（服务端大模型 QA + 客户端 coding agent）替代分析与编码人力。


二、目标
----------------------------------------------------------------
G1 提供统一 issue 录入入口，覆盖需求与 bug。
G2 基于知识库自动完成准入判定与项目分拣，减少人工分派。
G3 按预设工作流编排执行，通过 CS 反向长连接驱动责任人客户端落地。
G4 每个环节过程文档回传服务端集中可见。
G5 录入/判定/查看/执行做基于角色的权限控制。
G6 所有 AI 调用（变量替换后最终 prompt + 调用日志）服务端可观测。
G7 服务端统一配置 coding agent 与 prompt，支持按客户端差异化，并提供监控视图。


三、用户故事
----------------------------------------------------------------
US-1 作为产品经理，我希望在页面录入 issue（业务/类型/描述/期望完成时间/责任人），以便
     统一收口需求与缺陷。
US-2 作为平台，我希望基于知识库自动判定 issue 是否准入，以便减少人工初筛。
US-3 作为平台，我希望依据 issue 内容识别关联项目并拿到 Git 地址，以便自动分拣。
US-4 作为研发负责人，我希望系统按工作流自动拉起客户端执行，以便少做上下文交代。
US-5 作为研发工程师，我希望 coding agent 基于本地代码生成概要/详设/故障报告初稿，以便
     我只做确认而非从零写。
US-6 作为管理者，我希望在服务端看到每个客户端连接状态、CodingAgent 配置状态、作业状态，
     以便掌握全局运行。
US-7 作为平台管理员，我希望在服务端统一配置 prompt 与 coding agent（模型/限额），并支持
     给不同客户端差异化，以便集中治理。
US-8 作为审计/合规，我希望看到每次 AI 调用的渲染后 prompt 与日志，以便排查与溯源。


四、术语与角色
----------------------------------------------------------------
术语：
- issue：一条需求或 bug 记录。
- 准入判定：判断 issue 是否可进入执行流程。
- 分拣：识别 issue 关联项目并解析 Git 地址。
- 工作流：需求流 / Bug 流 的节点序列。
- coding agent：客户端侧执行文档生成与编码的 AI 代理，支持多后端。
- 反向长连接：客户端 daemon 主动连服务端建持久 gRPC 流。

角色（RBAC）：管理员、录入人(产品)、责任人(研发)、评审人、测试、只读/管理者。


五、总体流程
----------------------------------------------------------------
录入 → 准入判定(服务端QA) → 项目分拣(服务端QA) → 工作流编排 → 客户端执行(反向gRPC)
  → 文档/日志回传 → 评审 → 验收。
需求流：拉取Git → 需求分析(概要) → 详细设计(设计) → 设计评审 → 编码 → 测试 → 验收
Bug流：  拉取Git → 问题分析(故障报告) → 方案设计(修复方案) → 设计评审 → 编码 → 测试 → 验收


六、功能需求（EARS）
================================================================

【模块 A：录入与状态机】  (F-01, F-02)
----------------------------------------------------------------
F-01 issue 录入页面
  Ubiquitous：系统 shall 提供 issue 录入页面，字段含业务、诉求类型(需求|bug)、
              诉求描述、期望完成时间、责任人；其中业务/类型/描述/期望完成时间/责任人为必填。
  Event-driven：当用户提交录入且必填项缺失时，系统 shall 拦截提交并高亮缺失字段及原因。
  Event-driven：当用户成功提交时，系统 shall 生成 issue 唯一标识并置为"草稿"或"待判定"。
  Optional：Where 录入人填写了优先级/关联模块/附件，系统 shall 一并保存并在详情展示。
  验收标准：
   - 必填五项缺失任一无法提交，提示明确。
   - 提交后生成唯一 ID，状态进入初始态。
   - 选填字段正确保存与展示。

F-02 issue 状态机
  Ubiquitous：系统 shall 维护 issue 状态：草稿/待判定/已准入/分拣中/执行中/阻塞/完成/打回。
  State-driven：While issue 处于"执行中"且某节点失败，系统 shall 将其置为"阻塞"并保留节点上下文。
  Event-driven：When 准入判定输出"不可准入"，系统 shall 置为"打回"并附原因，通知录入人。
  Unwanted：If 状态流转出现非法跃迁（如草稿直接跳完成），系统 shall 拒绝并记录审计日志。
  验收标准：
   - 仅允许预定义合法跃迁。
   - 阻塞/打回均带原因与上下文。
   - 任意流转留痕可查。

【模块 B：准入与分拣】  (F-03, F-04)
----------------------------------------------------------------
F-03 基于 KB 的准入判定
  Event-driven：When issue 进入"待判定"，系统 shall 调用服务端 LLM QA（结合 KB 检索）输出
              可准入/不可准入及原因。
  Unwanted：If AI 判定置信度低于阈值或命中高风险，系统 shall 转人工复核而非直接放行。
  State-driven：While 判定为"不可准入"，系统 shall 锁定该 issue 不进入分拣。
  验收标准：
   - 判定结果含结构化原因。
   - 低置信度自动转人工，不误放。
   - 判定记录（含调用日志）可回溯。

F-04 项目分拣
  Ubiquitous：系统 shall 维护业务→项目→Git 映射配置，供分拣优先匹配。
  Event-driven：When issue 已准入，系统 shall 依据业务/描述识别关联项目并解析 Git 地址；
              规则匹配命中时直接采用，未命中时由 LLM QA 模糊匹配兜底。
  Unwanted：If 无法解析出唯一 Git 地址，系统 shall 置"分拣中"待人工指定并通知。
  验收标准：
   - 命中映射表直接出地址。
   - 未命中有 AI 兜底且可人工修正。
   - 解析结果写入 issue 并可追溯。

【模块 C：编排与执行】  (F-05, F-06, F-07, F-08)
----------------------------------------------------------------
F-05 工作流模板
  Ubiquitous：系统 shall 预置需求流与 Bug 流两套模板，节点可配置。
  Event-driven：When 分拣完成，系统 shall 按 issue 类型实例化对应工作流。
  Optional：Where 管理员自定义节点顺序/新增节点，系统 shall 按配置实例化。
  验收标准：
   - 两套模板默认可用。
   - 实例化后节点与 issue 绑定。
   - 自定义模板生效且不破坏既有流。

F-06 客户端 daemon
  Ubiquitous：客户端 daemon（Go）shall 启动后向服务端注册并维持心跳。
  Event-driven：When 客户端首次注册，系统 shall 记录客户端标识、责任人、版本并拉取本人配置。
  Unwanted：If 心跳超时（默认 30s 无心跳），系统 shall 标记该客户端离线。
  验收标准：
   - 注册/心跳正常，服务端可见在线。
   - 离线判定及时准确。
   - 客户端能拉取本人配置。

F-07 任务下发（反向 gRPC 流）
  Ubiquitous：系统 shall 通过客户端已建立的持久 gRPC 流下发任务指令。
  Event-driven：When 工作流推进到某节点，系统 shall 将该节点任务推送给责任人客户端。
  Unwanted：If 下发失败或客户端离线，系统 shall 排队重试并告警（见 F-18）。
  验收标准：
   - 任务经已建立流下发，不依赖服务端主动入站。
   - 下发失败有重试与告警。
   - 任务带服务端签名，客户端仅执行指派给本人的任务。

F-08 过程文档回传与展示
  Event-driven：When 客户端 coding agent 产出文档，系统 shall 接收并关联到 issue 对应节点。
  Ubiquitous：系统 shall 在服务端按 issue 维度集中展示所有过程文档。
  Optional：Where 文档需责任人确认/修订，系统 shall 支持在线确认与版本留存。
  验收标准：
   - 文档按 issue+节点归档，服务端可见。
   - 修订有版本记录。
   - 文档存储方案落地（待定：本地/对象存储/复用SVN或Git）。

【模块 D：权限】  (F-09)
----------------------------------------------------------------
F-09 RBAC
  Ubiquitous：系统 shall 对录入/判定配置/查看/客户端执行/评审/管理做角色鉴权。
  Event-driven：When 用户访问 issue/文档/客户端，系统 shall 按其角色与指派关系校验权限。
  Unwanted：If 越权访问，系统 shall 拒绝并返回 403 并记录。
  验收标准：
   - 六类角色权限矩阵生效。
   - 责任人仅见本人相关 issue 与本人客户端。
   - 越权被拒并留痕。

【模块 E：AI-服务端 QA】  (F-10, F-12)
----------------------------------------------------------------
F-10 LLM QA 网关
  Ubiquitous：系统 shall 提供服务端 LLM QA 网关（千问/智普），仅用于准入/分拣/QA 问答。
  Event-driven：When 需准入/分拣/问答，系统 shall 调用网关并在 prompt 中注入 KB 检索结果(RAG)。
  Optional：Where 管理员切换模型，系统 shall 生效新模型并保留调用日志。
  验收标准：
   - 仅用于非代码场景（不生成文档）。
   - 模型可切换、有额度控制。
   - 调用日志服务端可查。

F-12 知识库管理
  Event-driven：When 上传文档到 KB，系统 shall 完成解析/切分/向量化并供检索。
  Ubiquitous：系统 shall 支持 KB 检索与版本管理。
  验收标准：
   - 上传文档可被检索并用于 RAG。
   - 版本可追溯。

【模块 F：AI-客户端 coding agent】  (F-11, F-19, F-20, F-21)
----------------------------------------------------------------
F-11 coding agent（文档生成+执行）
  Ubiquitous：coding agent shall 在客户端基于本地仓库完成文档生成（概要/详设/故障报告/
             修复方案/评审辅助）与故障分析/编码/测试执行。
  Event-driven：When 工作流到达文档/执行节点，系统 shall 调用客户端 coding agent 并按
              四道护栏执行（分支隔离/测试门禁/仅MR/失败回滚）。
  State-driven：While 编码节点，系统 shall 确保 agent 仅在独立 feature 分支操作，不直接改主干。
  Unwanted：If 自动测试不通过，系统 shall 禁止提 MR 并上报失败。
  Unwanted：If 构建/测试异常，系统 shall 自动 revert 并上报服务端。
  Optional：Where 使用公网后端(Claude/Cursor/Codex)分析代码，系统 shall 按 D4 允许但
           敏感仓库由服务端策略强制私有化后端。
  验收标准：
   - 文档在执行端生成并回传。
   - 四道护栏全部生效（分支/门禁/仅MR/回滚）。
   - 合并与验收保留人工闸门。

F-19 coding agent 多后端配置（服务端统管·按客户端差异化）
  Ubiquitous：系统 shall 支持为客户端配置多个 coding agent 后端
             （ClaudeCode/Cursor/Codex/CodeBuddy）。
  Event-driven：When 管理员保存某客户端配置，系统 shall 下发至该客户端并生效。
  Optional：Where 某客户端需差异化，系统 shall 允许覆盖默认配置（模型/限额）。
  验收标准：
   - 四后端可配。
   - 按客户端/责任人差异化生效。
   - 配置变更可下发并回显状态。

F-20 AI 调用日志与渲染 prompt 可观测
  Event-driven：When 客户端发起任意 AI 调用，系统 shall 接收"变量替换后最终 prompt +
              调用日志(模型/请求响应摘要/token/耗时/费用)"并关联 issue/agent。
  Ubiquitous：系统 shall 在 issue/agent 视图提供上述日志查询。
  验收标准：
   - 每次 AI 调用均有渲染后 prompt 与日志回传。
   - 可按 issue/客户端/模型检索。
   - 用于调试、审计、成本。

F-21 prompt 与模板配置治理
  Ubiquitous：系统 shall 将所有 AI prompt 与拼接模板置于配置文件（服务端统管），禁止硬编码。
  Event-driven：When 需拼接 prompt，系统 shall 用"模板+变量"渲染，变量由系统注入
              （issue字段/仓库上下文/KB结果/节点等）。
  Optional：Where 按客户端差异化，系统 shall 应用该客户端覆盖模板。
  验收标准：
   - 无硬编码 prompt。
   - 模板变量注入正确，渲染结果可回传核对。
   - 配置变更经服务端统一入口。

【模块 G：评审/通知/统计/集成/安全/容错】  (F-13~F-18)
----------------------------------------------------------------
F-13 评审结论回写
  Event-driven：When 评审人在详设评审/验收节点提交结论，系统 shall 回写至 issue 节点。
  验收标准：结论与节点绑定、可查。

F-14 通知
  Event-driven：When 任务到达/超时/被打回，系统 shall 通知对应责任人。
  验收标准：三类事件均有通知触达。

F-15 周期看板
  Optional：Where 管理者查看统计，系统 shall 展示吞吐、节点耗时、阻塞分布。
  验收标准：指标计算口径一致、可筛选。

F-16 Git 集成
  Event-driven：When 客户端执行拉取/分支/MR/commit，系统 shall 与 Git 平台交互并回写结果。
  验收标准：克隆/分支/MR/commit 成功回写（Git 平台待定）。

F-17 安全
  Ubiquitous：系统 shall 对客户端做身份认证、任务鉴权、传输 TLS 加密。
  Unwanted：If 客户端身份校验失败，系统 shall 拒绝其注册/收任务。
  验收标准：认证/鉴权/加密均生效。

F-18 容错
  Event-driven：When 客户端离线/任务超时/执行失败，系统 shall 重试并告警。
  验收标准：重试策略可配，告警触达。

【模块 H：监控】  (F-22)
----------------------------------------------------------------
F-22 服务端监控视图
  Ubiquitous：系统 shall 提供监控视图展示三类状态：客户端连接状态、各客户端 CodingAgent
             配置状态、作业(任务)状态与进度。
  Event-driven：When 客户端连接/断开/配置变更/作业状态变化，系统 shall 实时刷新视图。
  State-driven：While 客户端离线，系统 shall 在视图标记离线并提示最后心跳时间。
  验收标准：
   - 连接状态（在线/离线/最后心跳/版本）可见。
   - 各客户端 CodingAgent 后端/模型/限额/启用态可见。
   - 作业按 issue/客户端展示当前节点与成功/失败/阻塞。


七、交互说明（关键页面）
----------------------------------------------------------------
P1 录入页：必填五项 + 选填；提交即校验。
P2 issue 详情：状态机时间线、各节点文档、评审结论、AI 调用日志入口。
P3 工作流配置：需求/Bug 模板节点编排。
P4 CodingAgent 配置：后端列表(四者)、模型、限额；支持按客户端差异化覆盖。
P5 监控视图：客户端连接 / CodingAgent 配置 / 作业状态 三区。
P6 KB 管理：上传/检索/版本。
P7 权限管理：角色与成员指派。


八、数据指标 / 埋点
----------------------------------------------------------------
事件                      字段示例
issue_created              issue_id, 类型, 业务, 责任人, ts
issue_admitted             issue_id, 判定结果, 置信度, 是否转人工
issue_sorted               issue_id, 项目, git_url, 命中方式(规则/AI)
task_dispatched            issue_id, 节点, 客户端, ts
agent_call                 issue_id, 客户端, 后端, 模型, 渲染prompt_hash,
                            token, 耗时, 费用, 成功/失败
doc_uploaded               issue_id, 节点, 文档类型, 版本
client_heartbeat           客户端, 状态, 版本, ts
job_status_changed         issue_id, 节点, 旧态, 新态
建议口径：节点耗时 = 下发到回传完成；阻塞分布 = 按节点聚合"阻塞"次数；
         成本 = 按客户端/模型聚合 token 与费用。


九、验收标准汇总（上线门槛）
----------------------------------------------------------------
- 内网反向长连接打通，任务可下发、文档/日志可回传（F-06/F-07/F-08/F-20）。
- 需求流与 Bug 流端到端跑通，文档在执行端生成并服务端可见（F-05/F-11/F-08）。
- coding agent 四道护栏全部生效（F-11）。
- 服务端可统一配置 coding agent 与 prompt，且按客户端差异化（F-19/F-21/D5）。
- 监控视图三状态实时可见（F-22）。
- RBAC 六角色权限矩阵生效（F-09）。
- 准入判定低置信度转人工，不误放（F-03）。


十、边界与异常场景
----------------------------------------------------------------
- 客户端离线：任务排队重试，视图标记离线，恢复后继续（F-18/F-22）。
- 准入误判：低置信度转人工兜底（F-03）。
- 分拣歧义：无法唯一解析时转人工指定（F-04）。
- coding agent 改坏代码：分支隔离+测试门禁+仅MR+自动回滚四重保护（F-11）。
- 公网后端分析敏感代码：服务端策略强制私有化后端（D4/F-11）。
- prompt 渲染变量缺失：客户端上报渲染异常，服务端告警（F-21）。
