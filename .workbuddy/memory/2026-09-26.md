## 诊断：客户端接入链路缺口

用户反馈"客户端怎么接入平台没看懂，页面也没有文档指引"，逐层核查后结论：

### 接入机制（设计）
客户端位于 NAT 后，由 daemon **主动**向服务端 :9443 建 gRPC 双向流 `AgentService.Connect()`。
- 上行：REGISTER(首帧) → HEARTBEAT(10s) → TASK_RESULT → CALL_LOG → UploadArtifact(大文档)
- 下行：ConfigPush(注册即回推，GLOBAL 默认 + clientId 覆盖合并) → TASK_DISPATCH(HMAC-SHA256 签名) → COMMAND
- 服务端 30s 无心跳判 OFFLINE（ClientRegistry.isOnline）

### 服务端侧：完整
agent.proto / AgentGrpcService / ClientRegistry / ClientSink / DispatchService / ConfigService / ClientController 均已实现。

### 客户端侧：只有半个壳（核心缺口）
`client/src` 仅有 AgentConfig、ConfigStore、PromptRenderer 三个工具类。
- **缺 `AgentApplication` 主类**：pom.xml shade 插件 Main-Class 指向 `com.yonyong.talos.agent.AgentApplication`，但类不存在；解包 talos-agent.jar 验证，仅含 3 个工具类 + gRPC 生成类 → `java -jar` 必然 ClassNotFoundException
- 缺 gRPC stub 调用代码（无 ManagedChannel / 双向流实现）
- 缺 重连退避 / 心跳循环 / 任务执行 / agent CLI 适配层 / 四道护栏
- `client/conf/`、`client/scripts/` 为空目录；无 install.bat
- Register 未校验 token（设计文档要求校验）

### 前端缺口
- 控制台 12 页无"接入指南"入口；Docs.tsx 是业务过程文档，非接入文档
- 两处接入说明互相矛盾：Download.tsx（install.bat / 内置 JRE / talos-agent.exe --keepalive）vs Clients.tsx（TalosAgent.exe install --server ... --token）
- Landing 页脚"部署文档 / API 参考"为 href="#" 死链
- Clients.tsx 操作按钮（重连/下发配置/查看日志）均为 toast 假动作，未接后端 API

### 技术栈分歧
技术方案设计 V0.1 写客户端用 Go 1.22 + grpc-go 单文件 daemon；
实际 client/ 是 Java 17 + Maven shade 打 fat jar。需用户确认方向。

## 原型设计评审（第二轮 5 项质疑，逐条代码核查）

1. **总览页卡片/Issue 不可点击**：`Dashboard.tsx` 的 Kpi 无 onClick（`ui.tsx:75` Kpi 组件根本没这 prop）；「近期 Issue」表行无 onClick（对比 `Issues.tsx:109` 有 `cursor:pointer` + setDetail）；「需要关注」告警行也无。仅页头两个按钮可用。
2. **无业务管理/仓库管理模块**：`server/.../entity/` 无 Biz/Repo 实体。分拣逻辑 = `AdmissionService.guessProject()` 关键词 if-else 硬编码（行情→quote-service、回测→backtest-api、账户→account-center、资讯→research-search，兜底 unknown-project）+ repoUrl 拼 `git@git.yonyong.dev:{p}/{p}.git`；责任人由前端下拉人工选，**完全不参与分拣**。用户表虽存 bizDomain/clientId 但分拣未用。KB 仅 5 篇规范类文档（DataInitializer.initKb）。
3. **Issue 详情只读**：详情 Modal 只有「关闭」按钮，无编辑/改派/启动工作流/删除。后端 `/api/issues/{code}/start`、`/api/workflows/instances/{code}/advance` 已实现，但 `web/src/api.ts` 未封装 → UI 触达不到。进度视图只在「作业监控」页，Issue 详情无跳转入口。
4. **langchain4j 只是壳，不是编排引擎**：`LlmService`（ChatLanguageModel）+ `PromptRenderService`（PromptTemplate）用到 langchain4j；但编排是手写线性引擎 `WorkflowService.advance()` → `filter(step == step+1)`，无 DAG/条件边/并行；唯一判断是 `gateDecision()` 的 pass/blocked 二值。NodeKind 只有 git/doc/code/test/rev，无 condition 类型。UI 副标题「langchain4j 编排」属过度宣称。另：gate 判定 `pass = out==null || !out.contains("blocked")` — **失败默认放行**，是隐患。
5. **Agent 配置形态与设计不符**：`AgentConfigEntity` 存 httpEndpoint/apiKey/temperature（HTTP API 形态），设计文档 §5.3 明确「调本地 CLI/进程」。且 `ConfigService.buildPush()` 只下发 backend/model/enabled/tokenLimit/privateOnly，**baseUrl/Key 存了但从未下发**（Agents 页「保存并下发」实际丢失这两项）。

## 客户端静默升级 / 一键脚本 / 查看日志（第二轮）

### 需求
1. 客户端支持静默升级（服务端下发 → 后台下载校验替换重启，研发无感）
2. 一键安装 + 一键启动（双击即用）
3. 「查看日志」只有一个空弹框 → 做成真实三视图日志

### 关键环境结论（都是实测出来的，别再猜）
- **cmd 的重定向失败不会设置 errorlevel**。`type nul >>file 2>nul` 在被占用时报
  「另一个程序正在使用此文件」但 errorlevel 仍是 0 → 不能用 errorlevel 探测。
- **可靠的占用探测是 `ren`**：`ren "logs\agent.log" "logs\agent.log.probe"`，
  文件被别的进程持有（无 FILE_SHARE_DELETE）时 ren 失败且 errorlevel=1。
  探测后要 ren 回来。`findstr` 写哨兵回读也能用，但会污染日志。
- **运行中的 JVM 锁着自己的 jar**，进程内 `Files.copy` 必然 AccessDenied →
  自替换不可能，必须由外部进程在旧进程退出后替换。
- **无控制台父进程下**：`start` 静默失败、`powershell` 直接卡住；只有
  `ProcessBuilder` 直接调 `cmd /c 脚本` 可用。
- **ProcessBuilder 拉起的子进程在父进程退出后能存活**（用 T.java 验证过：
  java 派生 cmd → java 退出 → 子进程继续跑完全部 tick）。所以「升级后客户端
  没起来」不是进程被回收，而是脚本自己中断。

### 踩过的坑与最终方案
- `logs\agent.log` 由**派生 agent 的那个 cmd 的重定向**持有，释放时间晚于 JVM。
  新会话重定向到被占用的 agent.log 会**直接中断整个 run-agent.bat**（真正的
  「升级后客户端再也没起来」成因）。
  最终方案：`run-agent.bat` 启动时用 ren 探测一次，拿不到就本次会话改写
  `logs\agent-<id>.log`；`AgentLogTail.logFile()` 改成取 logs 下**最新的
  `agent*.log`**（并列时优先 agent.log），`status.bat` 同步改。控制台始终跟当前会话。
- `apply-upgrade.bat` **不要**去等 agent.log 变可写：实测它会长时间不释放，
  30 次重试把升级 stall 掉约 90 秒（还会被外层超时打断）。等日志交给 run-agent.bat。
- `apply-upgrade.bat` 保留「等旧 PID 退出」（`tasklist /FI "PID eq X" | find`），
  这是 jar 能干净替换的前提；脚本头加了 flow 第 0 步。
- 服务端**旧连接 onCompleted 晚于新连接 REGISTER**（实测差约 70ms）→
  `registry.unregister(clientId)` 会把刚重启上线的客户端误置 OFFLINE，
  控制台显示离线、心跳还在、拉日志报「客户端离线」。
  修复：`ClientRegistry` 的 Entry 增加 `owner`，`register(id, sink, owner)` +
  `unregister(id, owner)` 按归属判断（`sinks.remove(key, entry)` 原子删除），
  保留无 owner 的强制 `unregister(id)` 给心跳超时巡检用。

### 实测结果
- 静默升级全链路通：`STARTED → APPLYING → RESTARTING → 新进程上线`，
  **停机窗口约 1~2 秒**；upgrade.log 有 `old pid X exited (0s)` / `jar replaced
  (attempts: 0)` / `starting agent ...`；新会话因 agent.log 被占写 fallback 日志。
- 客户端 21 源文件 `mvn package` + `build-package.bat` BUILD SUCCESS（1.4.2）
- web `npm run build` 通过（55 模块），已 `cp -r web/dist/. server/src/main/resources/static/`
- server `mvn -DskipTests compile` 通过；**jar 未重打包**（见遗留）

### 遗留 / 下一步
- **server jar 需重打包**：用户 8080 实例锁住 `server/target/talos-server-1.4.2.jar`，
  `mvn clean package` 报 `Failed to delete ...talos-server-1.4.2.jar`。
  顺序必须是「先停服务端 → 我打包 → 用户再用 talos.bat 起」。控制台新 UI
  （日志弹框 + 升级入口）要等这一步才生效。

## 「客户端离线 → 点重连」的悖论排查（服务端三处修正）

用户报：控制台对某客户端点「重连」，提示「客户端离线，无法下发指令；它会在下次心跳周期自行重连」，
质问这是不是悖论、到底怎么才能把客户端拉起来。

### 结论
- **不是悖论，是必然**：客户端在 NAT 后，服务端**没有入站通道**，`isOnline=false` 时任何下行
  （重连 / 升级 / 配置 / 任务）都送不出去。「重连」按钮的语义只是**给已建连的流说「断了重建」**，
  它**不是拉起按钮**。真正的拉起只能在该客户端本机做（`scripts\start.bat` / 守护计划任务）。
- **但原提示文案是错的**：离线客户端不会再发心跳，所谓「下次心跳周期自行重连」永远不成立。
  唯一能自愈的情形是「**进程还活着** + gRPC keepAlive 探到流断了」→ `AgentDaemon.run()`
  退避 1→2→4…60s 重建（此时也不需要人去点重连）。

### 修掉的真 bug（「怎么点都拉不起来」的根因）
1. `ClientMonitorService.sweepOffline()` 判离线时**顺手 `registry.unregister(id)` 删掉 sink**。
   `ClientRegistry.heartbeat()` 只在 sink 存在时才刷 `lastSeen` → sink 一删就再也认不回该客户端：
   流还活着、心跳还在发、实体状态被 heartbeat 改回 ONLINE，下一次巡检又置 OFFLINE ——
   状态在列表上反复横跳，而所有下发永远返回「离线」，**永不自愈**。
   → 改为**只改状态、不删 sink**（sink 生命周期归连接的 onError/onCompleted）。
2. `AgentGrpcService.heartbeat()` 不做补登记。→ 加**心跳自愈**：`registry.get(clientId)==null`
   就用当前连接 `register` 回来，再刷 lastSeen。为此把 sink 包装抽成 `sink()` 方法 +
   `downstream` 字段（`register(payload, out)` 的 `out` 参数因此去掉）。
3. `ClientController.reconnect` 的 `hint` 改为可执行的真话：进程活着 ≤60s 自愈；
   进程已退出则**只能本机 `scripts\start.bat`**。

### 现场事实
本机没有 `C:/Talos` 安装副本，`client/` 与 `client/dist/talos-agent-1.4.2/` 下都**没有 `agent*.log`**，
`netstat` 也没有到 9443 的 ESTABLISHED → 这次是**客户端进程真的没在跑**，所以控制台显示离线是正确的。
8080/9443 由 PID 14088（用户常驻 jar）占用。
